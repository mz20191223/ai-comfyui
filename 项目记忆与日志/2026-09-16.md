# 2026-09-16 · 短剧工作台

## 一、看板页「loading 太久」根因定位与修复（重点）

用户反馈 `#/p/1/board?ep=1` 加载太慢。实测定位：

| 接口 | 改前 | 改后 |
|---|---|---|
| `GET /episodes/1/shots` | **54,905 ms** | **6.8 ms** |
| `GET /episodes/2/shots` | 45,402 ms | 4.7 ms |
| `GET /episodes/3/shots` | 28,179 ms | 4.3 ms |
| `GET /projects/1/overview` | 2,682 ms | 3.8 ms |
| `GET /projects/1/episodes` | 1,169 ms | 2.9 ms |

### 根因（两层，第一层是量级主因）

1. **`db.py` 每次查询都新建 SQLite 连接**。本机装了绿盾过滤驱动，`sqlite3.connect()` 单次 **10~30ms**，而一条查询只要 **0.14ms**（差 180 倍）。基准实测：单连接复用 340 次查询 = 48ms；每次新建连接 340 次 = 10.6 秒。
   - `list_shots` 是逐镜 N+1：34 镜 × 每镜 10 次查询 = 340 次连接。
   - 顺带发现：`PRAGMA journal_mode=WAL` 每条连接都设是浪费（它是**库级持久属性**，设一次写在库头，后续连接自动继承），每次连接都设会去抢写锁。
2. **`list_shots` 逐镜 N+1**（次要，但该修）。批量后 340 次查询 → 8 次。

### 修复

- `backend/app/core/db.py`：改为**每线程一条连接长期复用**（`threading.local()`）。`get_conn()` 语义变为「事务边界」——只 commit/rollback，**不 close**；新增 `close_conn()` 供脚本收尾。`journal_mode=WAL` 移入 `init_db()` 只设一次。
  - 安全性：`get_conn` 原只在 `db.py` 内部使用，无外部调用、无人 `.close()` → 改动面极小。
- `backend/app/services/shot_service.py`：`list_shots` 改按集批量查（新增 `_chunks/_placeholders/_grouped_by_shot` 助手，`_MAX_VARS=900` 防空占位符超限）。`aggregate_task_state` 抽出 `_task_state_from(rows)` 供单镜/批量共用；`_shot_status_summary` 抽出 `_frames_map`。
- **验证方式（值得复用）**：写了「黄金参照」脚本，把改动前的逐镜实现原样照抄一份，与新版逐字段比对，`json.dumps(sort_keys=True)` 必须逐字节相同。**这个手法当场抓出一处真实差异**（批量版多带出了分组用的 `shot_id`）。三集全部一致后才替换。

### 剩余 2.2s 不是应用问题

首行仍要 2.2s，导航计时暴露真凶：
```
fetchStart        1
domainLookupStart 1623   ← 请求发出前就等了 1.62 秒
```
是 **Chrome 的代理解析/自动探测（WPAD）**，不是页面代码。用 `--no-proxy-server` 启动后：加载前排队 **1572ms → 1ms**，DCL 1852ms → **324ms**。
→ 浏览器实测若见到恒定多出的 ~1.5s，先怀疑代理探测，用 `--no-proxy-server` 排除，别去优化前端。

## 六、就绪态四枚举的完整流转（用户提问，已逐写入点核实）

### 全部写入点（6 处）

| 写入值 | 位置 | 触发 |
|---|---|---|
| `draft` | `schema.sql:107` DEFAULT / `importer.py:166-168` | 建表默认 / 导入时**新插入**镜头 |
| `extracting` `pending_confirm` `ready` | `importer.py:526-545` `_recompute_readiness(ep_id)` | **整集重算**，导入流程末尾调（`importer.py:144`） |
| 同上 | `shots.py:193-205` `_refresh_readiness(shot_id)` | **单镜重算**，候选裁决后调（`shots.py:189`） |
| `ready`（强制） | `shots.py:112-118` `POST /shots/{id}/confirm` | 人工确认闸门，写 `confirmed_at` + 强制 `readiness='ready'` |
| `ready`（直写） | `creation.py:228-231` `POST /episodes/{id}/split` | 剧本拆解建镜 |
| `ready`（直写） | `shots.py:551-552` `POST /episodes/{id}/shots` | 手工新建镜头 |
| 任意 | `shots.py:23` `SHOT_FIELDS` 含 `readiness` | `PATCH /shots/{id}` 通用更新也能手工改 |

### 重算规则（两个函数完全一致）

```
if not has_detail:            extracting      # shot_details 无行
elif pending or pending_dlg:  pending_confirm # 任一类候选有 pending
else:                         ready
```
- `pending` = `shot_candidates` 里 `candidate_status='pending'` 的条数
- `pending_dlg` = `shot_dialogue_candidates` 里同口径条数

**关键：重算永不产生 `draft`。** `draft` 只在导入新插入的那一瞬存在，紧接着同一流程末尾就被重算覆盖 → 实际上是个**幽灵态**（当前 87 镜中 draft=0、extracting=0）。

### 数据自检（2026-09-16）

- 87 镜按规则重算：**0 个与现值不符** → 规则被严格执行（每次导入都整集重算）。
- `confirmed_at` **全部为 NULL** → 确认闸门从未被使用（前端也无调用点）。

### ★ 两处设计矛盾（已发现，未修）

1. **确认闸门与重算规则互相打架**：`POST /confirm` 强制置 `ready` 并写 `confirmed_at`，但**下次任何导入**触发 `_recompute_readiness` 会按候选重新判定 → 若候选还没裁决，刚确认的镜头被打回 `pending_confirm`，**确认白做**。
2. **`ready` 直写不建 `shot_details`**：手工新建镜头（`shots.py:551`）和剧本拆解（`creation.py:228`）直接写 `readiness='ready'`，但都不插入 `shot_details`。下次重算时 `has_detail` 为假 → 被打回 **`extracting`**，状态"看起来变坏"。
3. 补充：`POST /shots/{id}/unconfirm`（`shots.py:122-124`）只清 `confirmed_at`，**不还原 `readiness`** → 与 confirm 不对称。

### 候选裁决链路（与就绪态配套）

`POST /shots/{id}/candidates/{cid}` 支持三动作：`ignore`（置 ignored）、`link`（挂到已有资产，或 `create_asset=true` 时新建资产并挂图）、`reset`（退回 pending）；每次动作后调 `_refresh_readiness`。

## 探针误报修正（`probe_oprow.cjs`）
- 现象：巡检报「资产库 表格0个 · 行0条」并计入异常，`oprow_exit=2`。
- 排查：`probe_page.cjs` 实测资产库**完全正常**——内文 793 字、30 个资产（角色 12 / 场景 10 / 道具 8）、控制台 0 报错、0 失败请求。根因是该页是**卡片网格布局**（`Assets.vue` 里根本没有 `el-table`，用的 `a-card` 式网格），探针按「表格页」去量自然量不到 → 误报。

## 09-16 晚七：镜头详情页三个视频参数（前端 + 离线核验）
- 用户问「时长 / 分辨率 / seed 三个参数是干嘛的、有没有实际作用、没用就注销」。

  1) 三个控件各加小标签「时长（秒）/ 分辨率 / seed（可空）」（`.vid-params` + `.pf-label`，`align-items: flex-end`）；
  2) 下方加一行说明「这三个会原样写进视频请求体（点预览请求体可核对）：分辨率留空则用项目默认；seed 留空＝每次都重新随机，填了就固定复现同一版」；

- 顺带确认渲染顺序是 `ref_audio_0` 在前、`ref_image_0` 在后，与「上传先音频后图片」的约定一致。
