## 二、12 个值得直接借鉴的设计（按对我们的价值排序）

### ★1. 状态机必须"双轨"：就绪态 ≠ 生成态
**来源：Jellyfish `sql/003-normalize-shot-status-remove-generating.sql`**

他们的迁移注释写得很直白：

> 新逻辑下 shot.status 仅表示"**信息提取确认状态**"：pending / ready
> 运行中的生成任务应从 GenerationTask 动态聚合，**不再写入 shots.status**

就绪判定用聚合子查询算出来：
- `skip_extraction=1` → ready
- `last_extracted_at IS NULL` → pending（区分"没提取"和"提取结果为空"）
- 候选总数=0 → ready
- 候选 pending 数=0 → ready
- 否则 pending

**对我们的意义（最关键的一条）**：你说的"我确认了就往下走"，本质是**就绪闸门**；而"正在生成中"是**任务态**。两者混在一张表会立刻出问题——重跑一次镜头，状态就乱了；任务失败后镜头卡在"生成中"永远出不来。所以：

- `shot.readiness`（信息是否齐备、是否已人工确认）——静态、由聚合算出
- `task.status`（跑没跑、跑到哪、成没成）——动态、独立任务表
- 界面上"待确认/已就绪"来自前者，"生成中/已出片"来自后者

### ★2. 提示词模板 = Jinja2 模板 + 变量声明 + 条件分支
**来源：Jellyfish `prompt_templates` 表**

字段：`category / name / preview / content / variables / is_system / is_default`

`content` 是真正的 Jinja2，含条件分支：

```
视觉风格：{{ visual_style }}   画面风格：{{ style }}
{%- if "古装" in style or "古代" in style -%}
modern clothing, modern background, contemporary elements
{%- endif -%}
```

`variables` 用 JSON 数组声明变量名，天然供前端渲染成表单。

**对我们的意义**：你的"四层结构（素材声明+不可变项+时序指令+风格）"、"接口A首行 I2VA/FL2VA 模板"、"防转场句"、"参考图 N 的取什么/不取什么"，全都可以做成模板 + 变量。**换剧换模板，不改代码**——这正是你要的"不写死"。

建议把 category 设计成：
`keyframe_image`（分镜图）/ `video_i2va` / `video_fl2va` / `video_ref2va` / `character_image` / `scene_image` / `prop_image` / `negative_base` / `transition_guard`（防转场句）

### ★3. 镜头拆主表 + 明细表（1:1 共享主键）
**来源：Jellyfish `Shot` + `ShotDetail`**

主表只放稳定字段（id / 章节 / 序号 / 标题 / 缩略图 / 状态 / 剧本摘录 / 成片文件），高频变化的细节全在 `ShotDetail`，注释写明"保持主表字段稳定"。

`ShotDetail` 里对我们尤其有用的字段：
- `camera_shot` 景别：ECU/CU/MCU/MS/MLS/LS/ELS
- `angle` 机位角度：EYE_LEVEL/HIGH_ANGLE/LOW_ANGLE/BIRD_EYE/DUTCH/OVER_SHOULDER
- `movement` 运镜：STATIC/PAN/TILT/DOLLY_IN/DOLLY_OUT/TRACK/CRANE/HANDHELD/STEADICAM/ZOOM_IN/ZOOM_OUT
- `duration` —— 注释写"**镜头唯一时长来源**"（单一事实源，避免多处各写一个时长）
- `override_video_ratio` —— **"为空表示继承项目默认"**（默认值 + 单点覆盖模式，后面 Provider 也照这个来）
- `action_beats`（JSON 数组）—— **按时间顺序的动作拍点**
- `first_frame_prompt` / `last_frame_prompt` / `key_frame_prompt` —— 三种帧的提示词分开存

**对我们的意义**：你现在的"0.0–0.6秒 / 0.6–4.8秒 / 4.8–6.0秒"这种时序指令，正好对应 `action_beats`；你反复纠结的"时长要 ≥ 音频实测"，正是因为需要 `duration` 这个唯一事实源。景别/机位/运镜三组枚举也正好对应 U55 截图里的"镜头设置"三步向导。

### ★4. 候选确认流：AI 抽出来的东西，人来「接受/忽略/关联」
**来源：Jellyfish `ShotExtractedCandidate` / `ShotExtractedDialogueCandidate`**

- 资产候选：`candidate_type`(character/scene/prop/costume) + `candidate_name` + `candidate_status`(**pending/linked/ignored**) + `linked_entity_id` + `payload`(JSON) + `confirmed_at`
- 对白候选**单独一张表**，注释说明理由："避免把对白确认流和实体关联流混在一起"，状态是 pending/**accepted**/ignored，接受后写 `linked_dialog_line_id`

**对我们的意义**：你导入现有剧本后，系统会抽出"过客/权限魅影/死循环妖/办公室"这些实体名。**每个都给你一个"关联到已有资产 / 忽略"的动作**，确认完这条镜头才 ready。这就是你要的"我确认没问题再往下走"，而且是**逐项**确认，不是一刀切。

### ★5. 资产一致性当一等公民（而不是附属功能）
**来源：Jellyfish + BigBanana**

- Jellyfish：`characters / actors / scenes / props / costumes` 五类实体，镜头通过 link 表引用；有 `AssetQualityLevel`(LOW/MEDIUM/HIGH/ULTRA) 表示"逐步补齐更多角度/细节图"，有 `AssetViewAngle`(FRONT/LEFT/RIGHT/BACK/THREE_QUARTER/TOP/DETAIL) 表示多视图
- BigBanana：**衣橱系统**（同一角色多套造型保持身份一致）+ **世界观锚点**（地图/区域/地点/音乐风格持续注入后续生成）+ **批量补齐缺失资产**（一键补齐角色/场景/道具缺失图片）
- BigBanana 的**上下文感知生成**：镜头生成时**自动读取**当前场景图、角色服装参考、道具参考 → 显著降低"不连戏"

**对我们的意义**：你的「参考图传不传」「同一人用参考图N」「角色图 vs 真实帧」这些判断，本质就是**资产引用**问题。工作台里做成：镜头勾选出场资产 → 参考图槽位与提示词的"参考图N"自动生成。**这是我方案里最核心的一条，跟 Jellyfish/BigBanana 完全一致。**

### ★6. 统一异步任务表（图/视频/文本共用一张）
**来源：Jellyfish `GenerationTask`**

```
mode          streaming / async_polling        ← 交付方式（决定用 SSE 还是轮询）
task_kind     script_divide / video_generation / image_generation  ← 执行器路由
status        pending/running/streaming/succeeded/failed/cancelled
progress      0-100 整数（前端直接展示）
payload       JSON 请求参数（快照，便于复现）
result        JSON 结果（url / metadata）
error         失败原因
cancel_requested / cancel_requested_at / cancel_reason / cancelled_at
started_at / finished_at
executor_type / executor_task_id              ← 预留外部执行器（celery 等）
```
索引是按轮询习惯建的（`status+updated_at`、`mode+updated_at`、`status+cancel_requested`）。

**对我们的意义**：视频生成动辄几分钟且经常要排队。你这套"跑一条 7 秒要等半天"的流程，必须能**关掉页面回来还在、能看到第几个、能取消、失败能重试**。`payload` 存快照这点对你也极重要——你经常需要"拿当时的参数原样再跑一遍"。

### ★7. Provider 按能力分 base_url（同一个供应商，图/视频不同地址）
**来源：Jellyfish `sql/005-add-provider-category-base-urls.sql`**

给 `providers` 表加了 `image_base_url` 和 `video_base_url`（"可选覆盖"，为空则继承主 `base_url`）。另有 006 迁移把"模型默认值"从 model 表迁到 `model_settings` 表，即**按类别设默认模型**。

**对我们的意义**：这正是"不写死"的第一层——**同一个 key，生图和生视频可能打不同网关**；且"按类别设默认 + 单次覆盖"的模式要贯彻到底。

### ★8. 关键帧驱动（Keyframe-Driven）：先画后动，治"抽卡废片"
**来源：BigBanana**

> 1. **先画后动**：先生成精准的起始帧 (Start) 和结束帧 (End)
> 2. **插值生成**：在两帧之间生成平滑过渡
> 3. **资产约束**：所有画面生成均受"角色定妆照"和"场景概念图"的强约束，杜绝人物变形

**对我们的意义**：这条直接解释了你项目里为什么 FL2VA/首尾帧比纯文生靠谱，也解释了你为什么反复"废片重跑"。工作台应该**把"首帧/尾帧"作为一等字段**（Jellyfish 的 `ShotFrameImage` 就是这么做的：`first/last/key` 三类型，每种至多一条），并在界面上明确显示"本镜是首尾帧模式还是多图参考模式"。

### ★9. 九宫格候选选帧：一次出 9 个视角，再选/裁一格当首帧
**来源：BigBanana**

> **九宫格分镜预览**：可先生成 9 个候选视角，再选择整图或裁切单格作为首帧，快速确认构图方案

**对我们的意义**：这可能是**最省你钱**的一条。你现在出分镜图是"一张一张抽"，抽到废的就重来。改成一次出 9 宫格（一张图的成本），你挑一格裁下来当首帧 —— 效率和废片率都会好很多。BigBanana 还支持"逐镜头决定用九宫格分镜还是首尾帧链路"（他们的**全自动计划预审**：批量生成前先给出生产方案让你过一遍）。

### ★10. 提示词管理页：集中检索 + 版本回滚 + 跨阶段排查
**来源：BigBanana Phase05**

> - 集中检索与编辑：统一查看模板、角色、场景、道具、关键帧和视频提示词
> - **版本回滚**：保留提示词编辑历史，可快速回退到旧版本
> - **跨阶段排查**：当结果不稳定时，可以直接回到这一页定位并修正上游提示词问题

**对我们的意义**：你改提示词是"精修 30 轮"的强度，**必须留版本历史**。项目里已经出现过"并行编辑丢字 7 处"的事故——有版本回滚就不会再慌。而且"跨阶段排查"正是你的真实场景：片子不对，是提示词问题还是参考图问题？

### ★11. 供应商配置化 + "可编程供应商"兜底
**来源：ilab-conjure（配置层）+ Toonflow（代码层）**

ilab-conjure 的供应商配置包含：Base URL / API Key / 图像模型 / **调用方式** / **并发上限**；支持 OpenAI-compatible 中转；**可分别绑定不同模型版本并自定义远端模型名**；网络设置提供"系统/直连/自定义代理"三种出口，**全局超时 1–30 分钟 + 重试 0–5 次**（长任务的必备项）。

Toonflow 更进一步——**可编程供应商系统**：

> 支持在设置中心直接编写供应商 TypeScript 逻辑并即时生效，**无需改源码或重启**

**对我们的意义**：分两层做。第一层是**声明式配置**（覆盖 90% 情况：改 endpoint、改字段名、改轮询路径）；第二层是**可编程适配器**（配置表达不了时，写一段小脚本转换请求/响应）。这样"换平台"永远是改配置，不改主程序。

### ★12. 提示词 chip 与模板分离 + 参数锁定
**来源：ilab-conjure**

- 三种 chip：`@` 图库 chip（选图并自动加入参考图 + 附加参考说明）、`#` 颜色 chip、`~` 提示词片段 chip（编辑器显示短标签，提交时展开全文）
- **模板 ≠ 片段**：模板是"长结构"，片段是"短原子"
- **输出参数一键锁定**，锁定时以只读摘要展示，"避免连续生成或浏览历史任务时误改设置"
- 单任务多图输出、**部分失败处理与失败重试**
- 历史任务收藏 + 标签 + **导出 ZIP（含各自提示词）**

**对我们的意义**：`@` chip 正好替代你"参考图槽位手填文件名"；`~` 片段正好装你的"防转场句""过客锁定句"；**参数锁定**能防你在连续跑镜头时误改 duration/resolution；导出 ZIP 带提示词，方便你归档复盘。配置备份/恢复（增量 or 替换）也值得照抄思路。

## 三、我们的方案 v1（已按调研结论修正）

### 3.1 分层

```
创作层  创意/剧本 → 角色·场景资产 → 分镜拆解 → 双份提示词生成
生产层  分镜图生成 → 【闸门1 图确认】 → 视频装配 → 【闸门2 参数确认】 → 生成 → 尾帧回流
```

### 3.3 Provider 配置化设计（**这是"不写死"的落地核心**）

分三层，从简到繁：

**第一层：声明式配置（覆盖绝大多数情况）**

```yaml
providers:
  - id: img-default
    name: "GPT-Image-2 中转"
    capabilities: [image]
    base_url: "https://<你的中转>/v1"
    api_key: "${ENV:IMG_KEY}"          # 支持环境变量引用，密钥不落库
    concurrency: 3
    timeout_sec: 600
    retry: 2

  - id: vid-oldplat
    name: "旧平台 MiniMax H3"
    capabilities: [video]
    base_url: "https://<旧平台>/v1"
    api_key: "${ENV:VIDEO_TOKEN}"
    concurrency: 2
    timeout_sec: 1800                  # 视频任务给足超时
    retry: 1

models:
  - provider: img-default
    category: image
    model: "gpt-image-2"
    remote_model_name: "gpt-image-2"   # 中转站自定义远端模型名
    mode: synchronous
    request:
      method: POST
      path: "/images/generations"      # 或 /images/edits（带参考图时）
      headers: { Content-Type: application/json }
      body: |                          # Jinja2：字段名随便改，不写死
        { "model": "{{ model }}",
          "prompt": {{ prompt | tojson }},
          "size": "{{ size }}", "n": {{ n }},
          "image": {{ ref_images | tojson }} }
    response:
      images: "$.data[*].b64_json"     # JSONPath 取结果（b64 或 url 都能接）
      images_url: "$.data[*].url"

  - provider: vid-oldplat
    category: video
    model: "minimax-h3"
    mode: asynchronous                 # 异步：提交拿 id → 轮询
    request:
      method: POST
      path: "/video_generation"
      body: |
        { "model": "{{ model }}",
          "prompt": {{ prompt | tojson }},
          "duration": {{ duration }},
          "resolution": "{{ resolution }}",
          "seed": {{ seed | default('null') }},
          {% for a in ref_audios %}"ref_audio_{{ loop.index0 }}": {{ a | tojson }},{% endfor %}
          {% for i in ref_images %}"ref_image_{{ loop.index0 }}": {{ i | tojson }},{% endfor %}
          "_last": 0 }
    response:
      task_id: "$.task_id"
    poll:
      path: "/query/video_generation?task_id={{ task_id }}"
      interval_sec: 5
      status_field: "$.status"
      success_values: ["Success", "succeeded"]
      fail_values: ["Fail", "failed"]
      result_video: "$.file_id"        # 或 $.video_url
      download_path: "/files/retrieve?file_id={{ result_video }}"
```

**关键设计点**：
- 请求体用 **Jinja2 模板**（学 Jellyfish），字段名/结构随便改 → 换平台只改这里
- 响应取值用 **JSONPath**（多打一层兼容，别假设字段名）
- **同步/异步两种交付模式**（学 Jellyfish `mode`）→ 生图多半同步、生视频必异步
- 按能力分 base_url（学 Jellyfish）→ 同一个 key 图/视频不同网关
- `--dry-run`：只渲染请求体不真发，便于对配置（学 ilab-conjure CLI）

**第二层：参数映射层**（用户填"时长=7、分辨率=768p竖"这类语义值，工作台按模型映射表转成该平台要的字面值，如 `768P`、`1080x1920`）

**第三层：可编程适配器**（P3 再上，学 Toonflow）：配置表达不了时，放一个小脚本文件做 request/response 转换，热加载生效，不改主程序。

### 3.4 状态机（**双轨，不要混**）

```
shot.readiness（静态，聚合算出，人工确认推进）
  draft → extracting → pending_confirm(有待确认候选) → ready
                                                      ↑
                              人工点「确认本镜」────────┘

generation_task.status（动态，每次生成一条）
  pending → running → succeeded / failed / cancelled
```
界面显示规则：镜头行显示 `readiness` 色块；同一行右侧小圆点显示**是否有在跑的任务**（从任务表聚合）。**绝不把"生成中"写进镜头状态。**

### 3.5 三个自动化钩子（省掉你现在九成手工）

1. **尾帧回流**：视频任务成功 → 自动 ffmpeg 抽尾帧 → 落 `视频尾帧\{shot}_tail.jpg` → 自动写入**下一镜**的 `shot_frames(first)` 与视频参数 `ref_image_0`
2. **音频时长校验**：音频素材挂到镜头后 → mutagen 精测时长 → 校验 `duration ≥ 音频时长 + 起始偏移`，不满足在镜头行标红（你手算过很多次的那个）
   - ⚠️ **音频不做生成**（2026-09-15 定）：配音在外部做好，工作台只负责「挂上素材 + 精测时长 + 作为 ref_audio_N 交给视频模型」。
     因此**没有 tts 类供应商/模型**，也没有 Edge TTS 那一套；镜头页的入口是「选择音频文件 / 更换音频 / 摘掉音频」。
3. **文件存在性校验**：所有引用的参考图/音频/首帧，生成前统一检查存在性（连 `.jpg` 后缀都要能容错），缺失直接拦

### 3.6 提示词 Lint（把项目铁律变成可开关规则）

点"生成"前自动扫，命中即在提示词旁标红：

| 规则 | 检查 |
|---|---|
| 跨镜交代 | 出现"承接上一镜 / 视线落点 / 上一镜尾帧"等词 |
| 缺防转场句 | 视频提示词未包含"严禁黑场、黑帧、淡入、淡出、溶解、叠化" |
| 台词格式 | 未加粗独立成句 / 被拆成多个 utterance |
| 白模禁入 | 参考素材里出现白模 mp4 |
| 时长不足 | `duration < 音频实测 + 偏移` |
| 主体越界 | 纯怪物镜头里出现人物词 / 单角色镜头描述其他角色 |
| 幽灵引用 | 提示词点名了未上传的参考图 |
| 内部代号 | 提示词里出现内部角色 ID（如"过客"）而参考图无对应视觉锚点 |
| 未上传却被引用 | Image N 声明了但 ref_image 列表里没有 |

### 3.7 界面结构（六段 + 两个向导）

1. **项目/集导航**（多剧并行）
